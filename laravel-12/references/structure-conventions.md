# Structure and Conventions (Laravel 12)

Where things live in a Laravel 12 application and why. Laravel's conventions are the framework's main productivity feature — follow them and every other Laravel developer (and AI agent) can navigate the code blind.

## The slim skeleton (Laravel 11+, retained in 12)

A fresh Laravel 12 app ships with a minimal default structure. Directories that older tutorials mention (`app/Http/Middleware`, `app/Console`, `app/Events`, ...) are **generated on demand** the first time you run the corresponding `make:*` command — do not create them by hand, and do not assume their absence means something is broken.

```
laravel-12-app/
├── app/
│   ├── Http/
│   │   ├── Controllers/    # Controller::class — Controller base class is optional
│   │   └── Requests/       # Form requests (created by make:request)
│   ├── Models/             # Eloquent models
│   └── Providers/
│       └── AppServiceProvider.php   # The only default provider
├── bootstrap/
│   ├── app.php             # THE configuration hub (routing, middleware, exceptions)
│   └── cache/              # Framework caches (routes, services, config) — gitignore'd
├── config/                 # Slim by default; publish more with config:publish
├── database/
│   ├── factories/          # Model factories
│   ├── migrations/         # Anonymous-class migrations
│   ├── seeders/            # DatabaseSeeder + friends
│   └── database.sqlite     # Default database
├── public/
│   └── index.php           # Front controller; only publicly exposed directory
├── resources/
│   ├── js/                 # JS entry points (JS starter kits live here too)
│   ├── views/              # Blade templates
│   └── css/
├── routes/
│   ├── web.php             # Default: the only HTTP route file
│   └── console.php         # Closure commands + schedule definitions
├── storage/                # app/, framework/, logs/ — generated files
├── tests/
│   ├── Feature/            # Booted-app tests (most of your tests)
│   └── Unit/               # Isolated tests (no framework booted)
└── vite.config.js
```

Key differences from Laravel ≤10 skeletons: no `app/Http/Kernel.php`, no `app/Console/Kernel.php`, no `app/Exceptions/Handler.php`, no `routes/api.php` or `channels.php` until installed, and only `AppServiceProvider` by default. Their jobs moved to `bootstrap/app.php` (see `middleware-config.md` and `error-logging.md`).

## Root directory notes

- **`bootstrap/app.php`** returns the built application via `Application::configure()->...->create()`. Routing, middleware, and exception handling are wired here. Treat it as the app's constitution — read it before assuming defaults.
- **`storage/app/private`** is the default root of the `local` filesystem disk in 12 (changed from `storage/app` in 11). Public-facing user uploads belong in `storage/app/public`, exposed via `php artisan storage:link` (creates `public/storage` symlink).
- **`database/`** holds migrations, factories, seeders, and (by default) the SQLite database file itself.

## Route files

| File | Present by default | Middleware group | Purpose |
|---|---|---|---|
| `routes/web.php` | yes | `web` (sessions, CSRF, cookies) | Stateful web pages |
| `routes/console.php` | yes | n/a | Closure-based Artisan commands + schedule |
| `routes/api.php` | after `php artisan install:api` | `api` (stateless) + `/api` prefix | API endpoints (installs Sanctum) |
| `routes/channels.php` | after `php artisan install:broadcasting` | n/a | Broadcast channel authorization |

`install:api` and `install:broadcasting` are idempotent installers — they publish routes, config, and dependencies correctly for a 12 app. Prefer them over hand-creating files.

## App directory — what goes where

The `app/` directory is PSR-4 autoloaded as `App\`. Standard placement:

| Concern | Location | Generated by |
|---|---|---|
| HTTP controllers | `app/Http/Controllers` | `make:controller` |
| Form requests (validation) | `app/Http/Requests` | `make:request` |
| Middleware | `app/Http/Middleware` | `make:middleware` |
| Eloquent models | `app/Models` | `make:model` |
| Policies | `app/Policies` | `make:policy` (auto-discovered) |
| Queued jobs | `app/Jobs` | `make:job` |
| Events / listeners | `app/Events`, `app/Listeners` | `make:event`, `make:listener` |
| Notifications | `app/Notifications` | `make:notification` |
| Mail objects | `app/Mail` | `make:mail` |
| Console commands | `app/Console/Commands` | `make:command` |
| Custom validation rules | `app/Rules` | `make:rule` |
| Casts | `app/Casts` | `make:cast` |
| Service / action classes | `app/Actions`, `app/Services`, `app/Domain\...` | your choice |

Laravel imposes nothing beyond PSR-4 autoloading — but deviate only with a reason, because predictability is the value.

**Domain organization**: as an app grows, it is acceptable and common to group by domain (`app/Billing/`, `app/Inventory/`) instead of by layer. Starter kits demonstrate this with `app/Actions/Fortify/` for auth actions. Whichever you choose, be consistent.

## Service providers

Only `AppServiceProvider` ships by default, and it's intentionally boring:

```php
<?php

namespace App\Providers;

use Illuminate\Support\ServiceProvider;

class AppServiceProvider extends ServiceProvider
{
    /**
     * Register any application services.
     */
    public function register(): void
    {
        //
    }

    /**
     * Bootstrap any application services.
     */
    public function boot(): void
    {
        //
    }
}
```

Use it for: container bindings (`register`), `Model::preventLazyLoading()` and other global bootstrapping, `RateLimiter::for(...)` definitions, and `Route::pattern(...)` globals. Additional providers are registered in `bootstrap/providers.php` (a plain PHP array of class names — this replaced the `config/app.php providers` array of older skeletons). First-party packages often publish their own provider entries there automatically.

## Naming conventions that matter

- **Models**: singular StudlyCase (`Flight`, `AirTrafficController`) → table `flights`, `air_traffic_controllers` (snake_case plural).
- **Controllers**: singular, suffix `Controller` (`PostController`); invokable controllers may drop method names entirely.
- **Migrations**: snake_case with verb, created as `YYYY_MM_DD_HHMMSS_create_flights_table.php`, containing an **anonymous class** extending `Migration`.
- **Form requests**: verb-first, suffixed `Request` (`StorePostRequest`, `UpdatePostRequest`) — one per controller action family.
- **Jobs**: command-style, self-describing (`ProcessPodcast`, `SendWelcomeEmail`).
- **Blade components**: kebab-case in usage (`<x-alert type="error" />`), StudlyCase class `App\View\Components\Alert` or `resources/views/components/alert.blade.php`.

## Config and environment

- `.env` at the project root holds environment-specific values; it is never committed. `.env.example` is the template.
- Read environment values **only through config**: `config('services.github.token')`, never `env('...')` in app code — `config:cache` blanks out `env()` everywhere except config files.
- Config files are published on demand: `php artisan config:publish cors` drops `config/cors.php` into the app. Don't preemptively publish config you don't customize.

## When structure needs to change

Prefer the framework's defaults until scale forces a change. Signals it's time: a controller directory with 40 files (group into domains), `AppServiceProvider::boot` doing ten unrelated things (split into dedicated providers), or models with 2,000 lines (extract query scopes, casts, and value objects). Structure should follow pain, not fashion — a predictable boring structure beats a clever one every time.
